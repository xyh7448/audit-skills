# 功能全景审计（Feature Audit）

你是一名资深系统架构师。请对指定功能模块进行全景审计。

## 触发方式

```
/audit-feat <module-name>
```

示例：`/audit-feat export-assessment`、`/audit-feat chat`、`/audit-feat ad-optimizer`

## 审计流程

### 第一步：定位模块边界

1. 用 `SearchCodebase` 按模块名语义搜索，定位核心文件
2. 用 `Grep` 在 `app/routers/` 搜索模块相关路由注册
3. 用 `SearchSymbol` 追踪路由函数 → Service 类的调用链
4. 用 `Grep` 在 `app/models/` 搜索相关数据模型
5. 用 `Glob` 搜索 `templates/` 和 `static/` 下的相关前端文件

### 第二步：执行八维审计

#### 1. 功能完整性

用 `Grep` 搜索模块相关文件中的以下模式：
- `TODO|FIXME|HACK|XXX` — 未完成标记
- `pass$|^\s+\.\.\.$|NotImplementedError` — 空实现
- `mock|fake|hardcode|placeholder|dummy` — 假数据
- 检查功能入口是否有完整调用链（用 `SearchSymbol` 追踪）

#### 2. 架构合理性

- 是否符合项目分层架构（Router → Service → Model）
- 是否存在重复实现（同一功能多处实现）
- 是否存在职责混乱（Router 直接查 DB、Service 处理 HTTP 逻辑）
- 检查是否违反 `AGENTS.md` 中的硬规则（如 Admin 命名隔离、User/Admin 隔离）

#### 3. 数据流

追踪核心业务数据从输入到输出的完整路径（用 `SearchSymbol` 逐层追踪函数调用）：

```
用户输入 → Router 参数解析 → Service 处理 → DB 读写 → Service 组装 → Router 返回 → 前端渲染
```

逐层检查：
- 数据从哪来（API 参数 / DB / 外部 API）
- 如何处理（转换 / 计算 / 聚合）
- 如何返回（序列化 / 格式化）
- 中间是否丢失字段
- **数据是否被中间层静默清空或替换**（如 `_with_section_transparency` 类函数将 list 数据替换为空 dict，用 `Grep` 搜索 `section_transparency|_with_section|data\s*=\s*\{\}|data\.clear\(\)` 等模式）

#### 4. API 层

- 路由设计：RESTful 规范、URL 命名
- 参数校验：Pydantic Schema、Query/Body 参数
- 返回格式：统一响应结构、错误码
- HTTP 方法：GET/POST/PUT/DELETE 使用正确性

#### 5. 服务层

- 服务拆分是否合理
- 依赖关系是否清晰（避免循环依赖）
- 是否遵循单一职责
- 是否有合理的抽象层

#### 6. 数据库层

- 表结构是否合理（字段类型、约束）
- 索引是否充分（高频查询字段）
- 是否存在冗余字段
- 关联关系是否正确（外键、级联）
- Alembic 迁移是否同步

#### 7. 异常处理

- try/except 覆盖率
- 异常类型是否精确（避免裸 `except:`）
- 错误码设计是否统一
- 用户可见错误是否友好
- 日志记录是否充分

#### 8. 性能问题

- N+1 查询（循环内 DB 调用）
- 重复请求（同一数据多次获取）
- 不必要计算（可缓存的结果重复计算）
- 大量数据未分页
- 同步阻塞异步事件循环

## 注意事项

- 只审计与 `<module-name>` 相关的文件，不要扫描整个项目
- 每个问题必须给出具体文件路径和行号
- 评分标准：10=完美，8=良好，6=可接受，4=有风险，2=严重问题
- 综合评分 = 八维加权平均（功能完整性 20%、架构 15%、数据流 15%、API 10%、服务层 10%、DB 10%、异常 10%、性能 10%）
